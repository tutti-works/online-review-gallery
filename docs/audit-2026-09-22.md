## 7. パフォーマンス・コスト評価

### 初回ギャラリー表示

- URL または保存済み gallery ID の確認に最大1 read、その後 `artworks` を1 query、admin のみ `likes` を1 query 行う。
- Firestore listener はなく、通常閲覧中の継続 read は発生しない。
- 一覧は各作品の先頭 thumbnail を使う。画像最適化プロキシは無効で、Storage から直接取得する。
- 現在の70〜100作品で実測不良は示されていないため、ページングや仮想化は保留する。

### モーダル・注釈・Konva

- モーダルを開いた時に原寸 WebP を表示し、注釈編集を有効にした時に `AnnotationCanvas` をロードする。
- Konva stage は一覧カードには存在しない。注釈操作中の描画負荷はあり得るが、現状コードだけから問題とは判定しない。
- 作品文書に注釈全文が含まれるため、データ量の将来増加だけは監視する。

### Showcase

- 入口は `galleries` と `showcaseGalleries` の全件、および featured 作品と更新元作品を読む。
- 詳細は gallery / showcase 各1件、curated ID ごとの作品、更新元ギャラリー作品を読む。
- 現状は read 数を debug flag で観測できる。集約キャッシュを先に作るより、実運用の read 数を保存して閾値を決める。

### インポート・Functions / Cloud Run

- 最大のコスト・待ち時間要因は、提出ごとの `userProfiles.get`、添付ごとの Drive metadata + media、全ファイルの一時 Storage 保存である。
- Functions 入口は最大100 instances、Cloud Run は手順上最大20 instances、Task は学生ごとに2秒ずつ遅延する。現在の規模で無制限 fan-out ではない。
- ただし入口側は処理を直列化して540秒まで待つため、Cloud Tasks を使っていても504を防げない。
- 公開画像の1年キャッシュと thumbnail は有効。ファイル名が一意なので cache invalidation の衝突も起こりにくい。

## 8. 現在の規模では対応不要

- Firestore listener への変更
- 作品一覧の仮想スクロール
- コメント・注釈の即時サブコレクション化
- Showcase の集約キャッシュや別検索基盤
- 削除専用キュー
- DDD、repository 層、状態管理ライブラリの導入
- Next.js / Firebase / Cloud Tasks / Cloud Run 構成の全面置換

これらは、実測した3秒超過、Firestore 文書肥大、競合、read 課金、削除失敗頻発などの条件が成立した場合に再検討する。
