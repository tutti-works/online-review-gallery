## 7. パフォーマンス・コスト評価

### 初回ギャラリー表示

- URL または保存済み gallery ID の確認に最大1 read、その後 `artworks` を1 query、admin のみ `likes` を1 query 行う。
- Firestore listener はなく、通常閲覧中の継続 read は発生しない。
- 一覧は各作品の先頭 thumbnail を使う。画像最適化プロキシは無効で、Storage から直接取得する。
- 現在の70〜100作品で実測不良は示されていないため、ページングや仮想化は保留する。

### モーダル・注釈・Konva

- モーダルを開いた時に原寸 WebP を表示し、注釈編集を有効にした時に `AnnotationCanvas` をロードする。
- Konva stage は一覧カードには存在しない。注釈操作中の描画負荷はあり得るが、現状コードだけから問題とは判定しない。
- 作品文書に注釈全文が含まれるため、データ量の将来増加だけは監視する。

### Showcase

- 入口は `galleries` と `showcaseGalleries` の全件、および featured 作品と更新元作品を読む。
- 詳細は gallery / showcase 各1件、curated ID ごとの作品、更新元ギャラリー作品を読む。
- 現状は read 数を debug flag で観測できる。集約キャッシュを先に作るより、実運用の read 数を保存して閾値を決める。

### インポート・Functions / Cloud Run

- 最大のコスト・待ち時間要因は、提出ごとの `userProfiles.get`、添付ごとの Drive metadata + media、全ファイルの一時 Storage 保存である。
- Functions 入口は最大100 instances、Cloud Run は手順上最大20 instances、Task は学生ごとに2秒ずつ遅延する。現在の規模で無制限 fan-out ではない。
- ただし入口側は処理を直列化して540秒まで待つため、Cloud Tasks を使っていても504を防げない。
- 公開画像の1年キャッシュと thumbnail は有効。ファイル名が一意なので cache invalidation の衝突も起こりにくい。

## 8. 現在の規模では対応不要

- Firestore listener への変更
- 作品一覧の仮想スクロール
- コメント・注釈の即時サブコレクション化
- Showcase の集約キャッシュや別検索基盤
- 削除専用キュー
- DDD、repository 層、状態管理ライブラリの導入
- Next.js / Firebase / Cloud Tasks / Cloud Run 構成の全面置換

これらは、実測した3秒超過、Firestore 文書肥大、競合、read 課金、削除失敗頻発などの条件が成立した場合に再検討する。

## 9. 次に切る実装 Issue の推奨順序

1. **HTTP Functions の Firebase ID トークン認証を共通化する**
   対象: import、status、artwork/gallery/all delete、count sync。本文メール認可・本番 admin 自動作成・token/個人情報ログも同時に除去する。
2. **依存脆弱性と Cloud Run Node.js 18 を解消する**
   Next / Sharp / Firebase / Google 系を段階更新し、未使用依存を除去する。画像・PDFの実コンテナ確認を完了条件にする。
3. **Storage を認証境界へ戻す移行計画と実装**
   Rules、`makePublic()`、既存 public ACL / download token、フロントの取得方式を一体で扱う。
4. **学生提出単位の進捗と冪等 Task を実装する**
   安定 student key、決定的 artwork / task ID、終端遷移 transaction、Task 投入失敗の終端化を含める。
5. **インポート入口の504と PDF 上限を解消する**
   profile Map、限定並列、事前サイズ・ページ検査、初期化 Task 化を計測付きで行う。
6. **削除・like・index の整合性を修正する**
   Showcase cleanup、補償削除、like transaction、`galleryId + createdAt` index をまとめる。
7. **高リスク経路のテストと CI、現行文書を整備する**
   認証・Rules・重送・進捗を先にテストし、Functions build と Rules test を CI へ追加する。

## 10. 実装前に人手で確認する外部状態

- 本番 Functions / Hosting / Cloud Run の revision と `main` の一致
- Cloud Run が未認証拒否で、Task 用 service account のみ `roles/run.invoker` を持つこと
- Storage の既存 public ACL と Firebase download token の実数
- Showcase 画像を学内ドメイン外へ公開する必要があるか
- Firestore の `galleryId + createdAt` 複合インデックス有無
- Firestore / Storage の backup、保持期間、復元実績
- 停止 job、重複 artwork、孤立画像、504 の発生件数
- `users.json` が実在人物のデータか、履歴除去・通知が必要か
